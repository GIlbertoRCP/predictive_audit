predictive-audit · a reproducibility study

Did the model beat yesterday?

I audited five published network-traffic forecasting results against the dumbest possible forecasts: the next value equals the current one, a short moving average, and the same value one cycle ago. Four of the five do not clearly beat them.

The bar every forecast has to clear

Network traffic, like most operational time series, is autocorrelated: the next five minutes look a lot like the last five. A forecaster that simply repeats the latest value, called persistence, gets a high score without learning anything. So a model's raw score says little; what matters is its margin over persistence.

Drag the slider to see how much "accuracy" autocorrelation hands out for free.

Case 01: my own model

Predictive_Activation v0 · CU Denver course project · congestion forecaster on Mininet telemetry

This project started with my team's course project, which reported a congestion forecaster with an F1 score around 0.99. It turned out the label was almost never changing: congested at the next step equalled congested now 98% of the time. On top of that, the evaluation shuffled overlapping windows before splitting, so the test set was full of near-copies of training examples.

Case 04: the traffic was on a loop

SDN-TMprediction · IEEE ICC 2021 · LSTM, BiLSTM, GRU on a Mininet testbed

This paper built an SDN testbed in Mininet, generated traffic by replaying packet captures with tcpreplay, and trained recurrent networks to predict each origin–destination flow from its last 10 minutes. The RNNs were compared only with each other.

Case 03: 785 LSTMs on real backbones

THU-INSC-NAD/Traffic-Matrix-Prediction · ISCC 2019 · Abilene, GÉANT, CERNET

The classic public traffic-matrix datasets come from real research backbones, sampled every 5 or 15 minutes. This codebase trains one LSTM per origin–destination pair and feeds the predictions into traffic engineering. I retrained all 785 non-trivial pairs with the repository's exact settings.

Pooled over each network, the LSTM is significantly worse than persistence on all three. A plain linear model on the same 10 inputs beats the LSTM everywhere. Running the configuration the code's own comments call "best" made the LSTM worse, not better.

Case 05: a reported number worse than "do nothing"

Annongkhanh/Traffic-matrix-prediction · LSTM on GÉANT and a Mininet testbed

Sometimes no retraining is needed. This project prints a single test error per dataset. Scoring trivial baselines on the same test cells, in the same scaled units, shows both numbers are worse than repeating the last traffic matrix.

Case 02: one that holds up

xiaochus/TrafficFlowPrediction · 681★ on GitHub · freeway flow (PeMS), LSTM / GRU / stacked autoencoders

An audit that fails everything would be worthless. This repository ships its trained weights, so I ran the exact published models. They reproduce the README to two decimals and genuinely beat every trivial baseline, by 8–10% MAE.

The headline number is still misleading: an R² of 0.94 sounds near-perfect, but persistence alone scores 0.92.

What to check before believing a forecast

  • Report persistence and a seasonal-naive baseline on the same rows, with the period chosen from training data. If the data loops or has daily cycles, the seasonal baseline is the one that matters.
  • Report the margin, with an interval that respects autocorrelation. A moving-block bootstrap, not an i.i.d. one.
  • Split by time. Shuffling overlapping windows before splitting puts near-copies of training data in the test set.
  • Distrust R² and accuracy on smooth or sticky series. Both are inflated by autocorrelation and class imbalance.
  • Include one simple learned model, such as a linear AR on the same inputs. In case 03 it beat the LSTM on every network.

Run the audit on your own result

uv run predictive-audit predictions.csv \
    --target y_next --pred model --group series --time t \
    --split split --season auto --metric mae --reported 0.123

The tool, every case's reproduction script, and the full per-case write-ups are in the repository.

Method notes. Third-party data and weights are fetched at a pinned commit and verified by SHA-256; none is redistributed beyond the small excerpts plotted here. Cases 03 and 04 are faithful re-implementations (single seed), case 02 runs the published weights, case 05 compares printed numbers. Each case's README lists its caveats.
